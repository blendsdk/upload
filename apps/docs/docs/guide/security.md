# Security

## Upload tokens

Session creation is an application-authenticated JSON request. The response contains a short-lived, session-bound upload token. tus requests use that token as a bearer credential; they do not rely on an application cookie, so long `PATCH` requests do not need CSRF protection and a stolen cookie is not enough to write bytes.

Tokens are signed with `tokenSecret`, bound to the session id, purpose and scope, and expire with the session. Keep the secret in the deployment secret store and rotate it with a planned restart. Do not put tokens in URLs or logs.

## Content validation

The server never trusts the browser MIME type:

- file-type magic-byte detection runs after the bytes arrive;
- declared and detected types must be compatible;
- image decoding uses sharp pixel limits and dimension checks;
- documents are served as attachments by default;
- file responses set `X-Content-Type-Options: nosniff` and a restrictive disposition.

Add a malware scanner as an `UploadProcessor` before making a document available if your threat model requires it. Do not serve untrusted PDF or Office content inline from the application origin.

## Access control

`authorizeSession` decides who may create a session and returns the owner/scope. `authorizeFile` decides who may read a stored file. Unauthorized file requests intentionally return 404 to avoid enumeration.

## Storage safety

Storage keys are generated by the server. User file names are display metadata only, are sanitized, and never become path segments. The local storage implementation hashes the scope and keeps files outside the web root.
